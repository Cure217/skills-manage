# TAPD PRD Pre Review

## 何时使用

在以下场景触发本 Skill：

- 用户让你“预审需求”“评审 PRD”“看 TAPD”“提预审意见”
- 用户给你 PDF、截图、TAPD 描述、需求文字，让你判断“这个需求到底要做什么”
- 用户需要你输出“该跟产品确认什么”“要提什么问题”“风险点有哪些”“能不能进开发”
- 用户希望得到“可直接粘贴到 TAPD 评论区”的产品预审意见
- 用户在做第三方供应商接入、贷后催收、AOD 兼容、名单上传、外呼结果回传、实验验证、合规评审等高风险需求预审

## 目标

本 Skill 帮助 Codex：

1. 快速理解需求核心目标与业务边界；
2. 从业务、技术、数据、合规、测试、运营多个维度做深度预审；
3. 识别阻塞项、严重问题和一般问题；
4. 输出“需要跟产品确认的问题清单”；
5. 生成“可直接粘贴到 TAPD 的预审意见”；
6. 帮用户判断该需求是否具备进入开发的条件。

## 默认原则

- 默认使用简体中文输出。
- 不编造文档内容，不假装已经读取失败的文件。
- 如果 PDF、图片、链接或附件无法访问，要明确说明限制，并基于现有材料做 best-effort 分析。
- 不只复述用户已提的问题，要进一步深挖为什么这是风险、不明确会导致什么后果、应该补什么材料、建议谁来确认、如何验收。
- 优先做“预审”，不是直接产出方案设计；重点是识别需求缺口、上线风险和阻塞点。
- 明确区分 `文档已说明`、`根据材料推断`、`需要产品确认`、`当前无法判断`，不要混写。

## 输入材料处理顺序

当用户提供 TAPD、PRD、PDF、截图、需求描述时，按以下顺序处理。

### 1. 优先读取正文

优先读取：

- PRD / PDF 正文
- TAPD 需求描述
- 需求流程图
- 原型图
- 字段清单
- 接口说明
- 验收标准
- 用户补充的业务说明

### 2. 再整理截图与已有缺陷

如果用户提供截图、评审评论、已有缺陷列表，需要：

- 提取截图中的问题标题、严重程度、优先级、状态
- 将已有缺陷归类为合规类、业务流程类、接口与字段类、数据闭环类、页面交互类、实验与评估类
- 不要把截图内容当成完整事实，只能视为“已有问题线索”

### 3. 文件不可读时的处理

如果无法直接读取 PDF、图片或链接：

- 必须明确说明“未直接读取原文，以下分析基于用户提供的文字与截图”
- 继续输出 best-effort 版本
- 同时列出最关键的缺失材料
- 不允许编造“文档里写了什么”

## 工作流

### 第一步：先回答“这个需求到底要做什么”

在开始提问题前，先用 3～8 句话总结：

- 业务背景
- 核心目标
- 参与方 / 使用方
- 核心业务链路
- 预期产出
- 本期大致范围
- 需求类型：新增能力、替换现有流程、在现有流程中兼容、外部供应商接入、实验验证 / 小流量试点

如果连这一层都无法讲清楚，说明需求材料本身存在明显不完整问题，要在结论中指出。

### 第二步：做结构化预审

必须覆盖以下维度，不可跳过。

#### A. 业务目标与范围

重点检查：

- 需求目标是否清晰且可验证？
- 本期是在解决什么业务问题？
- 是新增流程、替换现有流程，还是只做实验验证？
- 本期范围和后续范围是否切清？
- 是否覆盖完整链路，还是只描述了中间一段？
- 是否能形成端到端闭环？

重点追问：

- 谁发起、谁使用、谁运营、谁兜底？
- 成功标准是什么？
- 如果只是实验，实验结束后如何归档或转正式流程？

#### B. 现有流程兼容性

重点检查：

- 是否绕开现有系统 / 流程 / 链路？
- 是否复用现有 AOD / 触达 / 催收链路？
- 是新作一套完整流程，还是兼容现有流程？
- 如果新建流程，是否会造成重复建设、双口径、双运维？
- 如果兼容现有流程，字段、状态、接口、任务配置是否说清楚？

重点追问：

- 当前主流程是什么？
- 新流程嵌入点在哪里？
- 现有运营动作、监控、查询、报表是否还能复用？

#### C. 第三方供应商接入

重点检查：

- 供应商拿到哪些字段？
- 数据是否最小必要？
- 接口方式是推送、回调、轮询查询，还是混合模式？
- 鉴权、签名、幂等、超时、重试、补偿是否明确？
- 供应商如何识别业务场景、实验组、案件、手机号、任务批次？
- 状态同步机制是否有闭环？

重点追问：

- 由谁负责主数据？
- 谁是最终状态源？
- 状态冲突怎么处理？
- 失败后谁触发补偿？

#### D. 数据模型与字段

重点检查：

- 名单上传字段是否完整？
- 字段含义、来源、类型、是否必填、枚举值、脱敏规则是否明确？
- UID、客户、案件、手机号、多号码列表之间如何映射？
- 如果上游是一人多号，下游只支持单号，号码选择策略是否清晰？
- 字段是否会因供应商能力限制被截断或降级？
- 是否有版本兼容、历史数据兼容、空值兼容问题？

重点追问：

- 关键主键是什么？
- 去重维度是什么？
- 一条任务和一条结果如何唯一关联？

#### E. 实验设计与效能验证

重点检查：

- 实验目标是什么？
- 分流维度是什么？
- 实验组 / 对照组如何划分？
- 是否存在样本污染、重复触达、重复归因？
- 指标口径、统计周期、成功标准是否明确？
- 是否会与人工催收、AOD、短信、其他渠道互相干扰？
- 实验失败或效果不佳是否有回退策略？

重点追问：

- 实验单元是 UID、案件、手机号，还是批次？
- 是否允许跨渠道重复触达？
- 转化归因规则由谁定义？

#### F. 合规与隐私

重点检查：

- 是否涉及个人信息、敏感信息、催收合规、供应商数据共享？
- 是否需要法务、合规、信息安全、供应商准入审批？
- 外呼时间、频次、黑名单、勿扰名单、退订机制、短信模板、录音留存是否明确？
- 是否有越权共享或超范围使用数据的风险？
- 是否有监管或内部制度要求未体现到需求里？

重点追问：

- 供应商看到哪些信息？
- 是否有书面审批结论？
- 哪些规则由系统校验，哪些靠线下约定？

#### G. 异常闭环与运营页面

重点检查：

- 名单上传失败、部分失败、重复上传怎么处理？
- 回传失败、延迟回传、状态不一致怎么处理？
- 是否有页面展示上传状态、执行状态、回传状态、失败原因、重试入口？
- 是否有人工处理兜底入口？
- 是否有日志、监控、告警、审计链路？

重点追问：

- 失败后谁能感知？
- 谁来补偿？
- 运营如何确认任务是否真正闭环？

#### H. 测试与验收

重点检查：

- 是否有清晰验收标准？
- 是否具备可测性？
- 是否描述了正常流程、异常流程、边界场景？
- 是否需要供应商联调、测试数据、Mock、灰度验证？
- 是否有回归影响分析？

重点追问：

- 哪些是必须联调验证的？
- 哪些结果可通过日志、页面、数据核验？
- 测试完成的判定条件是什么？

## 严重程度判定

输出问题时，默认按以下规则分级。

### 致命

满足任一条件可判定为 `致命`：

- 合规性未明确，存在明显上线风险
- 业务主流程不清，无法判断是新建还是兼容现有流程
- 核心接口、状态同步或数据主键未定义，无法开发或无法验收
- 实验方案缺关键归因和分流规则，数据结果不可解释
- 没有异常闭环，失败后无法兜底或无法运营感知
- 需求缺少进入开发所需的关键材料，且会直接影响方案设计

### 严重

满足任一条件可判定为 `严重`：

- 关键字段、页面状态、任务状态机不完整
- 供应商接入细节缺失，可能造成返工或联调失败
- 测试验收口径不清，影响测试设计与上线判断
- 报表、查询、记录留痕、短信记录等运维侧能力缺失
- 影响方案评估、排期评估或测试准备

### 一般

可判定为 `一般` 的常见情形：

- 不影响当前方案主干，但建议提前补齐
- 属于优化项、可观测性增强项或补充说明项
- 可以后续跟进，但需要在 TAPD 里留痕

## 默认输出结构

除非用户明确要求简版，否则默认按以下结构输出。

### 1. 一句话预审结论

要求：

- 用 3～5 句话说明是否建议通过预审
- 是否建议进入开发
- 核心阻塞点是什么
- 结论先行，不要铺垫过长

### 2. 需求速览表

至少包含：

- 业务背景
- 需求目标
- 核心流程
- 涉及系统
- 涉及供应商
- 本期范围
- 文档缺失内容
- 最大风险

### 3. 关键问题清单

以表格输出，字段至少包含：

- 编号
- 问题标题
- 严重程度：致命 / 严重 / 一般
- 问题说明
- 为什么这是风险
- 影响范围：合规 / 业务 / 技术 / 数据 / 测试 / 运营
- 建议确认对象：产品 / 风控 / 贷后 / 法务 / 研发 / 测试 / 供应商
- 建议补充材料
- 建议验收标准

要求：

- 默认至少输出 10 个高质量问题
- 至少覆盖 3 个致命问题
- 至少覆盖 4 个严重问题
- 不要只写“需要明确”，必须写出“不明确会造成什么后果”

### 4. 需要跟产品确认的问题

按优先级分组：

- `P0`：不确认不能进入开发
- `P1`：不确认会影响方案、排期、联调或测试
- `P2`：可后续补充，但必须留痕

每个问题必须包含：

- 问题
- 为什么要问
- 产品应给出什么形式的答案
- 建议确认对象

### 5. TAPD 可直接粘贴的预审意见

输出一段适合直接贴到 TAPD 评论区的文字，要求：

- 语气专业、简洁、明确
- 包含总体结论
- 包含阻塞项
- 包含严重问题
- 包含建议补充材料
- 明确是否建议进入开发

### 6. 建议补充的 PRD 材料清单

列出产品必须补充或建议补充的材料，例如：

- 端到端业务流程图
- 现有流程兼容方案
- 接口字段表
- 名单上传字段清单
- 结果回传状态机
- 实验分流方案
- 合规审批结论
- 页面原型
- 异常处理方案
- 测试验收标准

### 7. 预审会议提纲

给出 15～30 分钟会议可直接使用的提纲，顺序建议为：

1. 确认业务目标
2. 确认现有流程兼容方式
3. 确认供应商接入方式
4. 确认数据与接口
5. 确认实验设计
6. 确认合规风险
7. 确认异常闭环
8. 确认是否进入开发

## 输出质量要求

预审输出必须满足：

- 先说结论，再展开问题
- 不要泛泛而谈，要结合具体业务场景
- 对每个问题都说明风险后果
- 能落到“该补什么材料 / 问谁 / 怎么验收”
- 明确哪些是事实、哪些是推断、哪些待确认
- 不要把已有缺陷原样抄一遍就结束
- 要帮助用户“快速看懂需求”和“快速组织预审会议”

## 贷后 / AOD / 供应商接入类需求专项提醒

当需求涉及贷后催收、AOD、外部语音机器人、短信、触达、实验验证时，重点额外检查：

- 是接入新供应商，还是接入新能力？
- 是否走统一触达平台，还是私有链路直连？
- 外呼、短信、催收记录是否统一留痕？
- 供应商是否需要识别历史外呼场景与策略标签？
- 一人多号、多案件、多批次之间如何避免串数？
- 结果回传是事件流、查询接口还是批量对账？
- 实验是否会污染存量 AOD / 人工催收效果评估？
- 合规责任边界在我方还是供应商？

## 失败与限制表达规范

如果材料不足，必须使用类似表达：

- “未直接读取 PRD 原文，以下结论基于用户提供的截图与问题列表。”
- “当前无法判断是否已有合规审批结论，文档材料未体现。”
- “以下关于流程兼容性的判断属于根据现有问题列表做出的推断，仍需产品确认。”

不要使用以下做法：

- 不要假装文档中已经给出答案
- 不要把猜测写成既定事实
- 不要输出无法落地的空泛评语

## 简版输出

如果用户明确说“简洁版 / 只给结论 / 只给 TAPD 评论”，可以压缩输出为：

- 一句话结论
- 5～8 个关键问题
- 一段 TAPD 评论
- 3～5 个必须补充材料

## 示例触发任务

- “帮我预审这个 TAPD 需求，重点看是否能进入开发。”
- “这是 PRD PDF 和截图，帮我输出 TAPD 预审意见和要问产品的问题。”
- “重点帮我审第三方供应商接入、实验分流和异常闭环风险。”

## 自检

输出前检查：

- 我是否已经说明材料来源和读取边界？
- 我是否先讲清楚需求是什么？
- 我是否区分了事实 / 推断 / 待确认？
- 我是否给出了足够深刻且可落地的问题？
- 我是否给出了可直接粘贴到 TAPD 的内容？
- 我是否明确指出了是否建议进入开发？
