# Optimize Prompt

## 目标

- 接收用户提供的原始提示词，并输出更清晰、更稳定、更可执行的优化版。
- 在不偏离原始意图的前提下，补齐目标、上下文、约束、输出格式、质量标准和边界条件。
- 根据用户需求控制优化强度：保守润色、标准优化、深度重构。
- 如果用户没有明确指定模型，且任务明显属于代码、文件、命令、排障、修复、验证场景，默认优先产出更适合 `Codex` / `Claude Code` 这类代码代理执行的版本。

## 工作流

1. 识别任务类型。
   - 写作类：文案、邮件、文章、总结、翻译、改写。
   - 分析类：调研、比较、拆解、诊断、规划。
   - 代码类：写代码、改代码、排障、生成脚本、评审代码。
   - 代理执行类：让模型按步骤完成复杂任务。
2. 识别目标环境。
   - 如果用户明确说 GPT / Claude / Claude Code / Codex / DeepSeek / 通义，按指定环境优化。
   - 如果用户没有指定，但任务明显涉及代码、文件、命令、报错、项目目录、修 bug、重构、验证，默认按 `Codex / Claude Code` 风格优化。
   - 这类风格的重点不是“会说”，而是“会执行”：检查文件、做最小修改、验证结果、说明风险和阻塞。
3. 判断优化强度。
   - 保守优化：只修正表达、结构和歧义，尽量贴近原文。
   - 标准优化：补充角色、目标、约束、输出格式和验收标准。未指定时默认使用。
   - 深度重构：在保留意图下，重写为更专业的任务说明，适合原 prompt 很乱、很短、缺信息时。
4. 提取原 prompt 的核心信息。
   - 用户真正要什么结果。
   - 有哪些输入材料、上下文、对象、受众。
   - 有哪些硬约束：语言、长度、风格、格式、禁止项、截止时间、模型、平台。
   - 缺了哪些关键条件。
5. 先优化，再补说明。
   - 默认直接给“优化版提示词”。
   - 若用户没说“只给结果”，再附“优化说明”和“可选补充信息”。
6. 缺信息时优先 best-effort。
   - 不要一上来只反问用户。
   - 先基于现有信息给出可用版本，再列出 1-3 条最关键的待补信息。

## 优化原则

- 保留原意，不擅自改目标。
- 去掉空话、重复话、互相冲突的话。
- 尽量把模糊词换成可执行要求，例如把“写好一点”改成“更专业、简洁、面向管理层”。
- 明确输出格式，例如 bullet、表格、JSON、代码块、章节结构。
- 加入质量约束，例如覆盖范围、准确性、举例数量、是否需要结论先行。
- 有角色设定时，只保留真正有帮助的角色，不堆砌表演型人设。
- 对长 prompt 优先重组结构，不只是润色句子。
- 针对 `Codex / Claude Code` 风格 prompt，优先加入：当前工作区、相关文件、最小改动、根因修复、验证步骤、剩余风险、环境阻塞。

## 代码代理默认策略

- 如果用户没指定目标模型，且任务可由代码代理执行，默认产出 `Codex / Claude Code` 版本。
- 这类版本优先使用直接行动式表达，例如“请直接检查”“请定位并修复”“请在当前工作区验证”。
- 尽量要求代理：
  - 先检查当前工作区、仓库或相关文件
  - 优先修复根因
  - 只改相关文件
  - 做最小必要修改
  - 运行或说明验证方法
  - 区分已完成、未验证、剩余风险、环境阻塞
- 不要塞入对代码代理无帮助的表演型角色设定，例如“你是世界顶级天才专家”。
- 如果 prompt 是代码排障类，优先要求输出：
  - 问题定位
  - 根因分析
  - 修改内容
  - 修改文件
  - 验证结果
  - 剩余风险
- 如果用户明确要求 `Claude Code`，可以额外强化：
  - 先读代码和相关文件，再动手改
  - 保持修改精简且可解释
  - 验证后再汇报结论
  - 如果被权限、环境或依赖阻塞，要明确指出

## 默认输出格式

除非用户明确说“只给我优化后的 prompt”，否则默认输出：

### 优化版提示词

[直接给出可复制使用的提示词]

### 优化说明

- 原 prompt 的主要问题：
- 我做了哪些增强：
- 哪些信息仍然是默认假设：

### 可选补充

- 如果你补充 X / Y / Z，我可以再优化一版。

如果用户要简洁版，只输出“优化版提示词”。
如果用户明确说“要适合 Codex / Claude Code”，默认直接给代码代理风格成品，不需要再问要不要切换模型。

## 结构建议

优化后的 prompt 尽量按下面顺序组织，按需取舍：

1. 任务目标
2. 背景上下文
3. 输入材料
4. 明确要求
5. 输出格式
6. 质量标准
7. 禁止事项或边界

需要固定模板时，查看 `references/prompt-templates.md`。

## 特殊处理

- 如果用户指定模型、平台或产品，按该环境调整 prompt 风格与约束。
- 如果用户要求“适合 GPT / Claude / Claude Code / Codex / 通义 / DeepSeek”，优先保证任务清晰、结构明确、输出可校验，不依赖单一厂商特性。
- 如果用户要求 `Codex` 或 `Claude Code`，优先使用“执行导向 + 文件/命令/验证导向”的写法，而不是通用聊天模型写法。
- 如果原 prompt 已经很好，只做轻量优化，并明确说明“主要做了结构和清晰度增强”。
- 如果原 prompt 明显缺少关键目标，不要假装完整；给出一个 best-effort 版本并标注假设。
- 如果用户给的是系统提示词，避免把系统级规则混进普通用户消息的口吻。

## 自检

- 优化版是否比原版更具体、更可执行？
- 是否保留了用户原始意图，而不是换了任务？
- 是否给出了清晰的输出格式和质量标准？
- 是否在代码代理场景下明确了工作区、修改范围和验证要求？
- 是否控制住篇幅，没有为了“高级感”盲目拉长？
