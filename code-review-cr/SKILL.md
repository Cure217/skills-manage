# Code Review CR

## 目标

- 对代码变更做可上线视角的 CR，不只指出问题，还要给出可执行修复建议。
- 区分主次问题、上线阻塞程度、影响面、风险等级和验证要求。
- 为关键问题生成可直接交给 `Codex` 或 `Claude Code` 的修复任务提示词。
- 保持评审基于证据：优先引用文件、函数、调用链、配置、测试或 diff 上下文。

## 工作流

1. 确认评审范围。
   - 优先查看用户提供的 diff、PR/MR 描述、变更文件列表、测试结果和相关上下文。
   - 如果在仓库内执行，优先使用 `git status`、`git diff --stat`、`git diff`、`git diff --cached`、`git show <commit>`、`git diff <base>...<head>`、`git log` 等命令确认范围。
   - 只评审本次变更相关内容；除非影响判断需要，不展开无关重构。

2. 构建上下文。
   - 查看被改代码的调用方、被调用方、测试、配置、迁移脚本、接口契约和发布路径。
   - 判断变更属于修 bug、新功能、重构、性能优化、配置变更、依赖升级、数据迁移还是发布脚本调整。
   - 标注不确定信息，不要把猜测写成确定结论。

3. 多角度检查。
   - **正确性**：逻辑分支、边界条件、异常路径、空值、类型、状态流转。
   - **兼容性**：API contract、数据结构、配置项、旧版本客户端、灰度和回滚。
   - **安全性**：鉴权、越权、注入、敏感信息、日志泄露、依赖风险。
   - **可靠性**：重试、幂等、超时、并发、事务一致性、降级、错误处理。
   - **性能**：复杂度、批量处理、数据库查询、缓存、I/O、内存和启动耗时。
   - **数据影响**：schema、迁移、默认值、历史数据、补偿任务、数据丢失风险。
   - **可观测性**：日志、指标、trace、告警、错误码、排障可见性。
   - **测试覆盖**：单测、集成测试、回归测试、边界用例、手工验证路径。
   - **可维护性**：重复逻辑、命名、模块边界、隐藏副作用、过度复杂实现。
   - **发布风险**：是否影响主链路、是否可灰度、是否可回滚、是否需要开关。

4. 分级判断。
   - `P0`：严重问题，通常阻塞上线；可能导致资损、数据破坏、安全漏洞、大面积不可用或无法回滚。
   - `P1`：高优问题，默认应阻塞上线；可能导致核心功能异常、兼容性破坏、明显稳定性风险。
   - `P2`：中优问题，可视发布窗口决定；影响局部场景、边界条件、可观测性或测试不足。
   - `P3`：低优问题，不阻塞上线；主要是可维护性、风格一致性、小范围优化建议。
   - `Nit`：非必须修改的轻量建议；不要让 Nit 淹没真正风险。

5. 判断上线影响。
   - 使用以下结论之一：`阻塞上线`、`建议修复后上线`、`风险确认后可上线`、`不影响上线`。
   - 同时说明影响面：用户范围、功能范围、数据范围、系统范围、发布/回滚范围。
   - 标准化影响等级：`局部`、`模块级`、`跨模块`、`全局`。
   - 如果证据不足，写清楚需要补充的验证材料或检查命令。
   - 即使没有发现阻塞问题，也要明确写出本次评审边界和未覆盖风险。

6. 生成代码代理修复建议。
   - 对每个 `P0` / `P1` 必须给出可复制给 `Codex` 或 `Claude Code` 的修复任务。
   - 对重要 `P2` 可按需给出修复任务。
   - 修复任务必须包含：问题、证据、目标文件、修改边界、禁止事项、验证方式、预期输出。
   - 不要只写“建议优化”；要写清楚“如何改、改哪里、如何验证”。

## 输出格式

使用以下结构输出 CR 结果：

````markdown
## CR 结论

- 总体结论：通过 / 有条件通过 / 不建议上线
- 是否影响上线：阻塞上线 / 建议修复后上线 / 风险确认后可上线 / 不影响上线
- 主要风险：用 1-3 条概括最重要风险
- 影响面：说明用户、功能、数据、系统、发布和回滚影响
- 建议下一步：先修哪些问题、补哪些验证、是否需要灰度或回滚预案

## 主要问题

| 优先级 | 是否阻塞上线 | 影响等级 / 影响面 | 位置 | 问题 | 证据 | 修复建议 |
|---|---|---|---|---|---|---|
| P1 | 建议修复后上线 | 模块级 / 示例：核心下单链路 | `path/to/file.ts` | 问题描述 | 具体证据 | 可执行建议 |

## 次要问题

| 优先级 | 是否阻塞上线 | 影响等级 / 影响面 | 位置 | 问题 | 建议 |
|---|---|---|---|---|---|

## Codex / Claude Code 修复任务

### 1. [P1] 问题标题

```text
请在当前仓库修复以下 CR 问题。

问题：
- 描述具体问题。

证据：
- 引用相关文件、函数、diff、调用链或测试现象。

修改范围：
- 优先修改：`path/to/file`
- 如需修改其他文件，必须说明原因。
- 不要做无关重构，不要顺手修复本 CR 未覆盖的问题。

修复要求：
- 说明期望行为。
- 覆盖边界条件。
- 保持现有接口兼容，除非明确说明需要破坏性变更。

验证要求：
- 运行或补充相关测试。
- 如果无法运行测试，说明原因，并给出建议的验证命令或手工验证步骤。

输出要求：
- 列出修改文件。
- 说明根因、修复方式、验证结果和剩余风险。
```

## 需要补充的信息

- 如果存在无法确认的风险，在这里列出需要用户或仓库补充的信息。
- 不要把不确定项伪装成确定缺陷。
````

## 质量要求

- 结论先行，优先突出会影响上线的问题。
- 每个高优问题都要有证据和可执行修复方向。
- 影响面尽量标准化到 `局部`、`模块级`、`跨模块`、`全局`，避免只写笼统描述。
- 不因个人偏好提出大量风格问题；风格问题只在影响维护成本或一致性时提出。
- 不要虚构不存在的文件、测试、日志或业务规则。
- 如果评审范围不足，明确说明“基于当前可见变更”。
- 默认只做 CR；除非用户明确要求“直接修复”，不要主动修改代码。

## 禁止事项

- 不要只输出泛泛建议，例如“建议加强测试”“建议优化性能”。
- 不要把所有问题都标成高优。
- 不要在没有证据时断言会导致线上故障。
- 不要扩大任务范围到无关重构、格式化全仓库或替换技术栈。
